Hexmapper: how it all clicks together

The shared West Marches world map — what each piece does, how an edit travels from one player's click to everyone's screen, and how to change the app safely in the future.

Part I

The big picture

One small Python server owns the map. Every player's browser is a thin canvas client connected to it over a WebSocket. There is exactly one copy of the truth — the SQLite file on the Fly.io volume — and everything else is a view of it.

The original pygame desktop app still lives in src/hexmapper/ and is untouched — the web version reuses its map model (a dictionary of hexes keyed by axial coordinates q, r), its 19 terrain colours, its icon PNGs, and its .hexmap save format, so maps can move between the two.

Part II

What lives where

PathWhat it is
web/index.htmlThe whole UI: sidebar, terrain palette, tool buttons, styles.
web/app.jsThe client. Hex math, canvas rendering, pan/zoom, tools, and the WebSocket sync logic. No framework, no build step — edit and refresh.
server/src/hexserver/app.pyFastAPI app: serves the web files and icons, the REST snapshot/export endpoints, the WebSocket hub that validates and broadcasts edits, and the invite-key gate.
server/src/hexserver/store.pyAll map state and SQLite persistence. Every edit type (set_hex, set_icon, remove_hex, add_layer, clear_all) is a method here.
server/src/hexserver/config.pyTerrain names/colours and the icon list. The client fetches these at load — change them here and every browser picks them up.
server/tests/pytest suite for the store logic.
src/hexmapper/assets/The icon PNGs (village, tower, ruin…). Shared by desktop and web.
Dockerfile + fly.tomlHow the app is packaged and where it runs.

Part III

How one edit travels

sequenceDiagram
    participant P as Player's browser
    participant S as FastAPI server
    participant D as SQLite
    participant O as Everyone else
    P->>P: paint hex locally (instant feedback)
    P->>S: {op: "set_hex", q, r, terrain}
    S->>S: validate terrain + op
    S->>D: write hex, bump version
    S->>O: broadcast op + version
    S->>P: broadcast op + version (confirms)

Conflicts are resolved per hex, last write wins — fine at party scale. If a browser drops offline it reconnects automatically and asks for a full snapshot, so nobody can get permanently out of sync. Invalid or unknown ops get an error frame back instead of crashing the connection.

Part IV

Making changes in the future

The development loop

  1. Run it locally. 
    cd server
uv run uvicorn hexserver.app:app --app-dir src --port 8321
    Open http://127.0.0.1:8321. Locally there is no key gate and the map is a throwaway local database — break things freely.
  2. Edit. Client changes (web/) need only a browser refresh. Server changes need a restart of the command above.
  3. Test and check. 
    cd server
uv run pytest tests
uv run ruff check src tests
uv run mypy --strict src/hexserver
  4. Commit with a conventional message (feat:, fix:, …) — pre-commit hooks enforce formatting.
  5. Deploy. With Docker Desktop running: 
    ~/.fly/bin/flyctl deploy --local-only --ha=false
    Fly builds the image, swaps the machine, and the party sees the new version on their next page load. The map database lives on the volume, so deploys never touch it.

Common recipes

Add a terrain type — add one line to TERRAINS in server/src/hexserver/config.py (name + hex colour). The palette in every browser updates on next load. Add the same entry to the desktop app's Terrain enum if you want desktop compatibility.

Add a map icon — drop a PNG into src/hexmapper/assets/ and add an entry to ICONS in the server's config.py. Redeploy.

Rotate the invite link (if it leaks): flyctl secrets set HEXMAP_KEY=<new-secret> -a hexmapper-west-marches. Old links and cookies stop working immediately; share the new ?key=… link. The current key is saved at ~/.hexmap-invite-key.txt.

Back up the world — the Export .hexmap button downloads the live map; keep one before big sessions. Fly also snapshots the volume daily (five kept). The exported file opens in the desktop editor too.

See what the server is doing — flyctl logs -a hexmapper-west-marches tails live logs, including any failed-op tracebacks.

Where it runs

  • URL: hexmapper-west-marches.fly.dev (players need the ?key=… invite link once; a year-long cookie does the rest).
  • Machine: one 256 MB instance in London that stops itself when nobody is connected and wakes on the next visit — expect roughly $1–2/month.
  • Storage: 1 GB volume at /data/map.db, survives every deploy and restart.

Not built yet, by choice: DM-only permissions (anyone can Clear all — the two-click confirm is the only guard), a map import endpoint, hex notes, and fog-of-war reveal mechanics. The design doc for the full plan is in docs/superpowers/specs/.
